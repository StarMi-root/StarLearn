# DeepSeek Harness 与 AI 编程工作流

“Harness”原意是马具，在 AI 工程中指**把模型能力约束并连接到真实环境的执行框架**。DeepSeek Harness 可以理解为围绕 DeepSeek 系列模型构建的编程 Agent 运行体系：模型负责推理，Harness 负责提供工具、上下文、沙箱、权限与反馈循环。

:::note 名称说明
不同团队和版本对 “DeepSeek Harness” 的具体实现、命令和仓库结构可能不同。本文讲的是这类系统的通用架构与使用方法，具体安装命令请以你使用的官方仓库文档为准。
:::

## Harness 与模型的分工

```text
┌────────────────────────────────────────────┐
│                 Harness                    │
│  任务规划 · 上下文管理 · 工具调用 · 沙箱   │
│  权限控制 · 测试反馈 · 日志与评估          │
└──────────────────┬─────────────────────────┘
                   │ 结构化请求 / 工具结果
┌──────────────────▼─────────────────────────┐
│              DeepSeek 模型                 │
│  理解代码 · 生成补丁 · 选择工具 · 解释错误 │
└────────────────────────────────────────────┘
```

- **模型**：根据上下文生成下一步行动或代码。
- **Harness**：把行动变成真实工具调用，例如读文件、搜索、执行命令、运行测试。
- **环境**：代码仓库、依赖、终端、浏览器、数据库。
- **反馈**：编译错误、测试失败、lint 结果会再次进入上下文，驱动下一轮修正。

没有 Harness，模型只能“聊天”；有了 Harness，它才能形成“观察 → 计划 → 行动 → 验证”的闭环。

## 核心组件

### 1. 上下文管理

Agent 不能把整个仓库塞进上下文。常见策略：

- 按任务检索相关文件；
- 用摘要压缩历史；
- 只保留最近工具输出；
- 对大型文件做符号索引；
- 记录任务计划与已完成步骤。

### 2. 工具层

典型工具：

| 工具 | 作用 |
|---|---|
| 读取文件 | 查看源码与配置 |
| 搜索 | 按关键词或符号定位 |
| 编辑文件 | 生成补丁 |
| 执行命令 | 构建、测试、格式化 |
| 浏览器 | 查文档、验证页面 |
| 数据库 | 查询结构或测试数据 |

工具应有明确的输入 schema、超时、输出上限和错误格式。

### 3. 沙箱与权限

AI 编程最大的风险不是“写错代码”，而是**执行了不该执行的命令**。Harness 应做到：

- 默认在隔离容器或受限目录运行；
- 危险命令需要人工确认；
- 限制网络与文件系统访问；
- 不把生产密钥放进环境；
- 所有操作可审计。

### 4. 反馈与评估

Agent 需要知道“做对了没有”。高质量反馈包括：

- 编译是否通过；
- 单元测试结果；
- lint 与类型检查；
- 性能基准；
- 代码审查意见。

没有验证的 Agent 只是在猜测。把测试接入循环，效果通常比换更大的模型更明显。

## 一个典型任务流程

用户：修复登录接口在 Token 过期时返回 500 的问题。

```text
1. 读取路由、认证中间件与相关测试
2. 搜索 Token 过期异常的处理位置
3. 提出修改计划
4. 修改错误处理，返回 401
5. 运行相关测试
6. 测试失败：断言期望 403
7. 阅读测试与产品文档，确认契约
8. 调整实现或测试
9. 运行完整测试套件
10. 输出变更摘要与风险说明
```

Harness 的价值在于让第 5、6、8 步自动发生，而不是让模型一次性写出“看起来对”的代码。

## 配置示例

不同 Harness 的配置格式不同，下面只是示意：

```yaml
model:
  provider: deepseek
  name: deepseek-chat
  temperature: 0.2

workspace:
  root: ./repo
  sandbox: docker
  allow_network: false

tools:
  - read_file
  - search
  - apply_patch
  - run_tests
  - git_diff

limits:
  max_steps: 40
  command_timeout_seconds: 120
  max_context_tokens: 64000

guardrails:
  require_approval:
    - rm
    - git push
    - kubectl apply
```

关键不是照抄字段，而是理解约束：模型能做什么、不能做什么、失败时如何停止。

## 与普通聊天式编程的区别

| 能力 | 聊天 | Harness |
|---|---|---|
| 读取整个项目 | 手动粘贴 | 按需检索 |
| 运行测试 | 人工执行 | 自动执行并回传 |
| 多步修改 | 容易丢失上下文 | 有计划与状态 |
| 安全边界 | 依赖用户 | 沙箱与权限策略 |
| 可复现性 | 较弱 | 日志、补丁、评估可追踪 |

## 什么时候值得用

适合：

- 有测试覆盖的代码库；
- 重复性重构、迁移、修 bug；
- 需要跨文件理解的改动；
- 文档、脚本与配置维护。

不适合：

- 没有测试且无法验证的高风险系统；
- 涉及生产数据库、支付、权限的核心变更；
- 需要人类判断产品取舍的任务；
- 法律、医疗等高风险决策。

## 使用建议

1. **小步提交**：一次任务只做一个明确目标。
2. **先写测试**：让 Agent 有可验证的完成标准。
3. **限制权限**：默认只读，写操作逐步放开。
4. **审查 Diff**：不要因为测试通过就直接合并。
5. **保留日志**：记录提示词、工具调用与结果，便于复盘。
6. **固定模型版本**：不同版本行为可能变化。

:::warn 安全底线
永远不要把生产密钥、用户数据、私有仓库凭证交给未加固的 Agent。执行删除、部署、数据库迁移前必须人工确认，并确保有备份与回滚方案。
:::

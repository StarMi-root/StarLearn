# AI 编程协作与本地 Agent 工作流

AI 编程工具已经从“补全一行代码”发展到“读取仓库、修改多文件、运行测试”。工具名称很多，但工作流可以归纳为：**给上下文 → 定边界 → 小步修改 → 自动验证 → 人工审查**。

## 工具地图

| 工具 | 主要形态 | 适合场景 | 关键注意点 |
| --- | --- | --- | --- |
| Codex | 云端/IDE 编程协作 | 生成代码、解释仓库、批量任务 | 审查变更，避免直接合并 |
| Claude Code | 终端 Agent | 多文件重构、测试修复 | 限制目录和命令权限 |
| OpenCode | 开源终端 Agent | 多模型、自定义工具、本地工作流 | 检查插件与模型配置 |
| Vibe Coding | 自然语言驱动原型 | 快速做 Demo、界面实验 | 原型不等于可维护产品 |
| Skills | 可复用技能/工作流 | 固化团队规范、重复任务 | 技能要版本化和测试 |
| Ollama | 本地模型运行 | 私有代码、离线实验 | 模型能力与显存有限 |
| Hermes Agent | Agent 运行框架 | 工具调用与任务编排 | 关注工具权限和审计 |
| Pi Agent | 轻量个人 Agent | 本地自动化、个人助手 | 不要暴露密钥和隐私 |
| DeepSeek Harness | 编程 Agent 运行体系 | 模型 + 工具 + 沙箱 + 反馈 | 先小仓库验证，再扩大范围 |

工具会更新，下面的原则比具体按钮更耐用。

## 1. 先给模型正确的上下文

低质量提示常见问题：只说“帮我修一下”，不给报错、文件和复现步骤。更好的任务描述：

```text
目标：修复 GET /api/users?page=2 返回 500。
现象：日志显示 NullReferenceException，位置 UserService.cs:42。
约束：不要改数据库结构；保持现有 API 返回格式。
验收：新增一个回归测试，dotnet test 全部通过。
```

上下文包括：项目结构、技术栈、相关文件、错误日志、已尝试方案、不能碰的目录、验收命令。上下文越准确，模型越少猜测。

## 2. 设定边界与权限

终端 Agent 可以执行命令，因此必须限制：

- 在独立分支或临时 worktree 中工作。
- 只允许读写项目目录，拒绝 `../` 和系统目录。
- 命令白名单：构建、测试、格式化可以执行；删除、发布、支付、发送邮件需要确认。
- 密钥不进入提示词、日志或提交记录。
- 对不可逆操作保留人工审批。
- 每次任务结束检查 `git diff`，不要盲目接受全部修改。

```bash
git switch -c ai/fix-login-500
# Agent 在此分支工作
git diff --stat
git diff
npm test
```

## 3. 小步修改，持续验证

把大任务拆成可验证的小步：

1. 复现问题，补一个失败测试。
2. 做最小修改，让测试通过。
3. 运行格式化、静态检查和完整测试。
4. 审查 diff，删除无关改动。
5. 写清楚变更说明和风险。

不要一次让 Agent 重写十个文件。改动越大，审查成本越高，隐藏回归越难发现。

## 4. Vibe Coding 的适用边界

Vibe Coding 指用自然语言快速描述意图，让 AI 生成并迭代代码。它适合：

- 快速验证产品想法和界面布局。
- 写一次性脚本、数据清洗和演示。
- 学习新框架时生成可运行起点。

不适合直接上线：

- 支付、认证、权限、隐私相关逻辑。
- 高并发、数据一致性、迁移脚本。
- 没有测试和审查的生产仓库。

原型完成后，必须补测试、错误处理、可访问性、性能和安全检查，把“能跑”变成“可维护”。

## 5. Skills：把重复工作流固化

Skill 是把指令、工具、脚本和验收标准封装成可复用单元。一个好的 Skill 应该：

- 有明确触发条件和使用边界。
- 步骤可执行，不依赖隐含上下文。
- 包含输入、输出和失败处理。
- 有版本号、变更记录和测试样例。
- 不把密钥、内部地址和敏感数据写死。

例如“生成数据库迁移”技能：

```text
输入：模型变更描述
步骤：
1. 检查现有迁移命名规范
2. 生成迁移文件
3. 运行迁移 dry-run
4. 输出 SQL diff 和回滚步骤
验收：dry-run 成功，回滚脚本存在
```

## 6. 本地模型与 Agent

Ollama 适合快速在本地运行模型；llama.cpp 更接近推理引擎，便于理解量化和参数；Hermes Agent、Pi Agent、DeepSeek Harness 则偏向 Agent 运行与工具编排。

本地部署的取舍：

| 维度 | 本地模型 | 云端 API |
| --- | --- | --- |
| 隐私 | 数据不出本机 | 需信任服务商 |
| 成本 | 前期硬件/运维成本 | 按量计费 |
| 能力 | 受显存和模型规模限制 | 通常更强 |
| 延迟 | 局域网低，冷启动慢 | 受网络影响 |
| 可控性 | 可换模型、可离线 | 受服务条款限制 |

本地 Agent 尤其要注意：模型可能生成危险命令，工具权限必须由代码控制，不能只靠提示词约束。

## 7. 评估与回归

不要用“感觉不错”评估 AI 编程效果。建立固定任务集：

- 10 个真实 bug 修复任务。
- 5 个多文件重构任务。
- 5 个需要写测试的任务。
- 记录成功率、平均步数、测试通过率、人工返工时间。
- 每次换模型或提示词后重跑。

同时保留失败案例。失败案例比成功演示更能说明边界。

## 8. 推荐日常流程

```text
1. 写清任务与验收标准
2. 创建分支/工作树
3. 让 Agent 只读分析，先给计划
4. 人工确认计划与权限
5. 小步修改，运行测试
6. 审查 diff，补充测试
7. 写变更说明，人工合并
```

:::tip 一个简单判断
如果一次 AI 变更你无法在 10 分钟内审查完，它可能太大了。拆小，再继续。
:::

## 练习：AI 编程工作流

:::quiz
question: 让 Agent 修复 bug 时，最重要的输入是？
options:
  - "更礼貌的语气"
  - "错误日志、复现步骤、约束和验收标准"
  - "更长的模型名称"
  - "关闭测试"
answer: B
explain: 准确上下文和验收标准决定任务是否可验证。
:::

:::quiz
question: 终端 Agent 的安全做法是？
options:
  - "允许删除任意目录"
  - "限制工作目录和命令白名单"
  - "把密钥写进提示词"
  - "自动合并所有修改"
answer: B
explain: 最小权限和人工审查是基本边界。
:::

:::quiz
question: Vibe Coding 最适合的场景是？
options:
  - "生产支付系统"
  - "快速原型和一次性脚本"
  - "数据库迁移审批"
  - "权限系统核心逻辑"
answer: B
explain: 原型迭代快，但生产代码需要测试、审查和安全加固。
:::

:::quiz
question: 一个好 Skill 不应该包含？
options:
  - "明确的输入输出"
  - "版本和测试样例"
  - "写死的密钥和内部地址"
  - "失败处理"
answer: C
explain: 密钥和敏感信息不能固化在技能里。
:::

:::quiz
question: 本地模型相比云端 API 的主要优势是？
options:
  - "一定更聪明"
  - "数据可控、可离线"
  - "不需要任何硬件"
  - "没有安全风险"
answer: B
explain: 本地部署提升数据控制力，但仍有模型和工具风险。
:::

:::quiz
question: 评估 AI 编程工具时，较可靠的指标是？

explain: 固定任务集和可量化结果比单次演示更可靠。
